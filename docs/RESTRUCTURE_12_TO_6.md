**構造を考えるうえで効く事実：**

- **11 データ入出力は他の10キーを横断する**。どの構造に入れても「その構造のもの」にならない、性質の異なる1枚。
- **1 コンディションだけ機微情報**でJSONバックアップから意図的に除外済み。構造を畳んでも**この除外は維持が必要**。
- 8 Quality Gate（347行）と 5 Prompt Builder（232行）で**全体の約3割**（579行 / 12枚計 1,873行 ＝ 約30.9%）。畳む対象として一番重い。

## 2. 6構造の名前は決まっているが、中身は未定義

`ROADMAP.md` と `PORTFOLIO_NOTE.md` に **North Star / Current / Bottleneck / Decisions / AI Office / Resume** の6語がある。
しかしリポジトリ全文を確認したところ、**6構造すべての定義と、12カードの割り当ては未確定**（`ROADMAP.md` に `Bottleneck` の一行説明があるだけ）。

- `Bottleneck` は既存12枚に対応物が無い（ROADMAP で「採用②＝新規カード」扱い）
- `North Star` も対応物が無い（Landing に近いが別物か未定）
- 残り4語に既存12枚をどう配るかは**未決**

→ **この配分を決めることが、そのまま情報設計＝Figma の作業。** ここから先は進めない。

## 3. しずくが Figma で決めること（決定リスト）

1. **6構造それぞれの定義**（1行ずつ）。特に `North Star` と `Bottleneck` は既存に無いので新規定義になる。
2. **12枚 → 6構造の配分**。1構造に何枚入るか、入れた中は「並列」か「主従」か。
3. **参照物2枚（Role Router / 世界観トークン）の扱い** — 構造の中に埋めるか、別の面（About / 折りたたみの奥）へ出すか。
4. **データ入出力の置き場所** — 6構造のどれかに属させるか、構造の外（footer 付近の道具）にするか。
5. **6構造を1画面に積むのか、切り替えるのか。** 積むなら縦の長さは今と大きく変わらない＝畳む意味が薄れる。切り替えるなら**ナビゲーションが新しく要る**（現在はハッシュルーティング2画面のみ）。
6. **各構造の見出しの見え方**（明朝か・余白・区切り線の有無）。

## 4. 実装側の前提（Figma が決まってから着手する）

- 保存キーは**変えない**。構造を畳んでも `shizuku.*` の10キーはそのまま使う（既存ユーザーのデータを壊さないため）。
- `projectId` 名前空間の作業は **PR #12 で main へ squash merge 済み**（`91d9659`・2026-09-05）。保存先は `scopedKey` 経由になっている。**この前提は確定したので**、構造変更はこの上に乗せる。
- **開閉状態のキーは日本語のカード名そのもの**（`src/components/Card.tsx` で確認：`shizuku.cardOpen.${title}`）。
  つまり**カード名を変えた瞬間、そのカードの開閉状態は無言で初期値へ戻る**（データ消失ではないが、体験は途切れる）。
  6構造で見出し名が変わるなら、移行するか・割り切るかを決める必要がある。なお `cardOpen` は
  `projectStorage.ts` の移行対象10キーには**含まれていない**（`condition` と同じ扱い）。
- 変更は必ず `npm run lint` / `typecheck` / `test` / `build` の4本を通してから区切る。

## 5. 止まっている理由（重要）

**Figma の file URL と node-id がリポジトリに存在しない**（ROADMAP 課題#3・`.ai/AUDIT_RESULT.json` でも同じ指摘）。
このプロジェクトは Figma をデザインの正本とするため、**正本を開けない状態で構造を決めることはできない。**
URL は**しずくしか出せない情報**で、推測で埋めてはいけない。
